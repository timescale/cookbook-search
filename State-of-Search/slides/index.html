A short history

PostgreSQL did not wake up one morning and discover search

early 2000stsearchcontrib work
2008FTS in corePostgreSQL 8.3
2021pgvectorvector type and IVFFlat
2023HNSWpgvector 0.5.0
2024+More physical choicesDiskANN, BM25, hybrid

Extensibility is the old trick powering the new tricks.

PostgreSQL arrays could store numbers. They did not provide embedding semantics, distance operators, or approximate nearest-neighbor indexes.

PostgreSQL 8.3 shipped full-text search in core on February 4, 2008. pgvector 0.1.0 dates to April 20, 2021. pgvector 0.5.0 added HNSW on August 28, 2023.

Sources: https://www.postgresql.org/docs/8.3/release-8-3.html, https://www.postgresql.org/docs/current/textsearch.html, https://www.postgresql.org/docs/current/arrays.html, https://github.com/pgvector/pgvector/blob/master/CHANGELOG.md

A tsvector stores normalized lexemes and positions. A tsquery expresses terms and logical or phrase relationships.

Native FTS remains a strong default when users know the vocabulary and the product needs PostgreSQL's parsing and query control.

Benchmark manners

“Fast” without context is fan fiction

corpus sizedimensionsfiltersupdate rate hardwarecache stateparametersconcurrency

Every ANN claim needs an exact baseline and a recall target.

Timescale reported 28 times lower p95 latency and 16 times higher query throughput than Pinecone at 99 percent recall. Keep the attribution and workload attached: 50 million 768-dimensional Cohere embeddings against Pinecone's s1 index.

That result deserves attention. It is not a universal law of physics.

Sources: https://docs.timescale.com/about/latest/changelog/ and https://www.timescale.com/newsroom/postgresql-is-now-faster-than-pinecone-75-cheaper-with-new-open-source

To sum things up

Match the retrieval method to the question

01Use exact and relational search when the query already has an identity.

02Add lexical, fuzzy, or semantic retrieval only when the question requires it.

03Measure approximate search against an exact baseline and a recall target.

04Add a second system when its product value pays for the operating boundary.

PostgreSQL covers enough of the stack to make that boundary a measured decision.

Recap the decision sequence. Begin with the shape of the question, then choose the smallest retrieval method that can answer it.

Exact lookup, fuzzy text, lexical ranking, semantic similarity, and hybrid retrieval solve different problems. Approximate indexes need an exact comparison. A dedicated engine needs enough product value to justify the consistency and ownership costs.

Final line for this slide: PostgreSQL does not replace every search engine. It covers enough of the stack that we can place the boundary from evidence instead of habit.
